# 鼠标移动导致满帧重绘 —— 问题报告

> 供外部求助用。可整篇复制到 GitHub issue / 论坛 / 给同事。
> 项目：minitor（Windows 资源监控），GUI 基于 eframe/egui 0.37 + glow(OpenGL)。
> 日期：2026-11-18

## 一句话

鼠标在窗口内**任意位置**滑动时，GUI 从 **1 帧/秒** 变成 **60 帧/秒**，CPU 从 0.6% 涨到接近**一个核心**（95–100%）；鼠标停下或移出窗口后立刻回落。

## 环境

| 项 | 值 |
| --- | --- |
| 系统 | Windows 11 26200 |
| CPU | Intel Core Ultra 7 155H（16C22T） |
| GPU | Intel Arc 核显，驱动 32.0.101.8826（OpenGL 3.3） |
| Rust / 框架 | eframe 0.37 / egui 0.37，`Renderer::Glow` |
| 窗口 | 1320×830，无 MSAA |
| vsync | 开（`GlowConfiguration { vsync: true }`，也是 eframe 默认） |
| 绘制方式 | 应用自己用 `Painter` 画卡片与曲线，几乎不用 egui 的 widget |

## 复现步骤

1. 启动 `minitor-gui`，鼠标移到窗口外，页脚显示 `1.0 帧/秒`
2. 鼠标在窗口内来回滑动（标题、卡片空白处、图表都行）→ 页脚变成 `60 帧/秒`
3. 鼠标静止约 1 秒内回落到 `1 帧/秒`

## 测量数据

CPU 为「占单个逻辑核的百分比」，用 `Process.TotalProcessorTime` 增量 / 时间窗 计算。

| 场景 | 帧率 | CPU |
| --- | --- | --- |
| 鼠标静止在窗口外/不动（窗口前台） | 1 fps | **0.5–0.9%** |
| **鼠标在窗口内滑动（窗口前台）** | **60 fps** | **95–100%** |
| 鼠标滑动（窗口不在前台） | 5 fps | 6.5% |
| 空白窗口（`ui()` 直接 return）+ 强制 60 fps | 60 fps | ~97% |
| 关闭 vsync + 滑动 | 97–888 fps | 17–118% |
| 关闭 vsync + 空闲 | 未受控 | 20–40% |

单帧内部耗时：

| 指标 | 值 | 来源 |
| --- | --- | --- |
| 我们自己的 `ui()` 全部逻辑 | **212 µs** | 应用内计时 |
| eframe `IntegrationInfo::cpu_usage`（含 egui 渲染） | **15.8 ms** | eframe 上报 |
| 连续渲染时单帧（vsync 关） | 1.1–1.3 ms | 帧数反推 |

结论：**帧的代价几乎全在呈现/等待，不在内容**——不画任何东西的空白窗口，在 60 fps 下同样要 97% CPU。

## 已经排除的可能

- **不是绘制量**：9 条曲线 × 60 点，空白 UI 同样贵。
- **不是字体/文本布局**：不画内容的帧一样贵。
- **不是采样或后台线程**：采样 0.7 ms/秒，与帧循环无关。
- **不是某个图表控件**：把图表的 `Sense` 改成 `Sense::empty()`（完全不响应悬停）后，滑动仍是 60 fps。
- **不是悬停提示（Tooltip）单独造成**：移除 Tooltip 后，一次测试降到 5 fps / 6.5%，另一次测试仍是 60 fps / 100%——**结果不稳定**，无法归因（见下）。
- **不是 `request_repaint_after(1s)` 写错**：应用中只有这一处主动请求，间隔 1 秒。

## 关键观察

1. **帧数与鼠标事件近似 1:1**。用脚本以约 60 次/秒 调用 `SetCursorPos` 移动鼠标，帧率就是 60；关闭 vsync 后同样脚本能跑到 97–888 fps。
2. 用 `Context::set_request_repaint_callback` 记录每帧的重绘请求：

   ```
   每帧请求数: 1    最新的 delay: 0 ms    帧耗时: ~500 µs
   ```

   前台空闲时也是**每帧一条 `delay = 0` 的请求、约 50 帧/秒**；窗口失去焦点后回落到 1 帧/秒。也就是说：**前台窗口每帧都会收到一个"立即重绘"请求**，而我们自己的代码只有 `request_repaint_after(1s)`。
3. 关闭 vsync 后，同样的空闲状态会**无上限连续渲染**（20–40% CPU），说明只要有待处理的重绘，eframe 就会不停跑；vsync 只是恰好把它压到 60。

## 想请教的问题

1. **eframe 0.37 + glow**：鼠标移动是否必然触发一帧？有没有**公开 API** 能把"输入驱动的重绘"限制到例如 10 fps，而不修改 egui/eframe 源码？
2. 前台窗口**每帧一条 `delay = 0`** 的重绘请求通常来自哪里（egui 内部？winit？eframe 的 `request_redraw`）？应用侧能否识别或抑制？
3. `set_request_repaint_callback` 只能观察、不能取消。有没有**更早的钩子**（winit 事件层、`event_loop_builder`）可以合并/丢弃鼠标移动事件，从而减少 `RedrawRequested`？
   - 已试：在 `App::raw_input_hook` 里丢弃 `PointerMoved` 并限流 50 ms → 滑动 CPU 从 101% 降到 71%，改善有限（推测重绘在事件到达时就已请求，钩子太晚）。
4. **Intel Arc 驱动在 `SwapBuffers` 等 vsync 时自旋**（每帧约 16 ms CPU 时间）是已知行为吗？切到 eframe 的 wgpu 后端（DXGI flip model，present 阻塞而非自旋）能否规避？代价大概是二进制 +多少 MB、运行内存 +多少？
5. 如果目标是把"鼠标移动"的开销压到 5% 以内，是不是必须放弃"每次输入都整窗重绘"的架构（egui 不支持局部重绘）？有没有在 egui 生态内的推荐做法？

## 验收标准

- 鼠标在窗口内移动时：**帧率 ≤ 10 fps，CPU < 5% 单核**
- 鼠标静止：**1 fps，CPU < 1%**
- 保留悬停提示与十字线

## 附：试过且无效/有副作用的方案

| 方案 | 结果 |
| --- | --- |
| 关闭 vsync | 滑动降到 17–23%，但空闲从 0.6% 涨到 20–40%（无上限渲染），不可接受 |
| `raw_input_hook` 丢弃/限流 PointerMoved | 101% → 71%，仍远高于目标 |
| 移除 Tooltip（改为图表内绘制读数） | 一次 5 fps/6.5%，另一次仍 60 fps/100%，不可复现 |
| 图表 `Sense::empty()` | 无变化 |
| 空白 UI | 60 fps 下仍 ~97%，证明与内容无关 |
