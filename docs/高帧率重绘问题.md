# 鼠标移动导致满帧重绘 —— 问题报告

> 供外部求助用。可整篇复制到 GitHub issue / 论坛 / 给同事。
> 项目：monitor（Windows 资源监控），GUI 基于 eframe/egui 0.37 + glow(OpenGL)。
> 日期：2026-11-18
>
> **状态：已解决。** 根因与修复见文末「解决方案」章节，实测已达标。
> 无需再外发求助；若仍要外发，可把两个章节一起复制。

## 一句话

鼠标在窗口内**任意位置**滑动时，GUI 从 **1 帧/秒** 变成 **60 帧/秒**，CPU 从 0.6% 涨到接近**一个核心**（95–100%）；鼠标停下或移出窗口后立刻回落。

## 环境

| 项 | 值 |
| --- | --- |
| 系统 | Windows 11 26200 |
| CPU | Intel Core Ultra 7 155H（16C22T） |
| GPU | Intel Arc 核显，驱动 32.0.101.8826（OpenGL 3.3） |
| Rust / 框架 | eframe 0.37 / egui 0.37，`Renderer::Glow` |
| 窗口 | 1320×830，无 MSAA |
| vsync | 开（`GlowConfiguration { vsync: true }`，也是 eframe 默认） |
| 绘制方式 | 应用自己用 `Painter` 画卡片与曲线，几乎不用 egui 的 widget |

## 复现步骤

1. 启动 `monitor-gui`，鼠标移到窗口外，页脚显示 `1.0 帧/秒`
2. 鼠标在窗口内来回滑动（标题、卡片空白处、图表都行）→ 页脚变成 `60 帧/秒`
3. 鼠标静止约 1 秒内回落到 `1 帧/秒`

## 测量数据

CPU 为「占单个逻辑核的百分比」，用 `Process.TotalProcessorTime` 增量 / 时间窗 计算。

| 场景 | 帧率 | CPU |
| --- | --- | --- |
| 鼠标静止在窗口外/不动（窗口前台） | 1 fps | **0.5–0.9%** |
| **鼠标在窗口内滑动（窗口前台）** | **60 fps** | **95–100%** |
| 鼠标滑动（窗口不在前台） | 5 fps | 6.5% |
| 空白窗口（`ui()` 直接 return）+ 强制 60 fps | 60 fps | ~97% |
| 关闭 vsync + 滑动 | 97–888 fps | 17–118% |
| 关闭 vsync + 空闲 | 未受控 | 20–40% |

单帧内部耗时：

| 指标 | 值 | 来源 |
| --- | --- | --- |
| 我们自己的 `ui()` 全部逻辑 | **212 µs** | 应用内计时 |
| eframe `IntegrationInfo::cpu_usage`（含 egui 渲染） | **15.8 ms** | eframe 上报 |
| 连续渲染时单帧（vsync 关） | 1.1–1.3 ms | 帧数反推 |

结论：**帧的代价几乎全在呈现/等待，不在内容**——不画任何东西的空白窗口，在 60 fps 下同样要 97% CPU。

## 已经排除的可能

- **不是绘制量**：9 条曲线 × 60 点，空白 UI 同样贵。
- **不是字体/文本布局**：不画内容的帧一样贵。
- **不是采样或后台线程**：采样 0.7 ms/秒，与帧循环无关。
- **不是某个图表控件**：把图表的 `Sense` 改成 `Sense::empty()`（完全不响应悬停）后，滑动仍是 60 fps。
- **不是悬停提示（Tooltip）单独造成**：移除 Tooltip 后，一次测试降到 5 fps / 6.5%，另一次测试仍是 60 fps / 100%——**结果不稳定**，无法归因（见下）。
- **不是 `request_repaint_after(1s)` 写错**：应用中只有这一处主动请求，间隔 1 秒。

## 关键观察

1. **帧数与鼠标事件近似 1:1**。用脚本以约 60 次/秒 调用 `SetCursorPos` 移动鼠标，帧率就是 60；关闭 vsync 后同样脚本能跑到 97–888 fps。
2. 用 `Context::set_request_repaint_callback` 记录每帧的重绘请求：

   ```
   每帧请求数: 1    最新的 delay: 0 ms    帧耗时: ~500 µs
   ```

   前台空闲时也是**每帧一条 `delay = 0` 的请求、约 50 帧/秒**；窗口失去焦点后回落到 1 帧/秒。也就是说：**前台窗口每帧都会收到一个"立即重绘"请求**，而我们自己的代码只有 `request_repaint_after(1s)`。
3. 关闭 vsync 后，同样的空闲状态会**无上限连续渲染**（20–40% CPU），说明只要有待处理的重绘，eframe 就会不停跑；vsync 只是恰好把它压到 60。

## 想请教的问题

1. **eframe 0.37 + glow**：鼠标移动是否必然触发一帧？有没有**公开 API** 能把"输入驱动的重绘"限制到例如 10 fps，而不修改 egui/eframe 源码？
2. 前台窗口**每帧一条 `delay = 0`** 的重绘请求通常来自哪里（egui 内部？winit？eframe 的 `request_redraw`）？应用侧能否识别或抑制？
3. `set_request_repaint_callback` 只能观察、不能取消。有没有**更早的钩子**（winit 事件层、`event_loop_builder`）可以合并/丢弃鼠标移动事件，从而减少 `RedrawRequested`？
   - 已试：在 `App::raw_input_hook` 里丢弃 `PointerMoved` 并限流 50 ms → 滑动 CPU 从 101% 降到 71%，改善有限（推测重绘在事件到达时就已请求，钩子太晚）。
4. **Intel Arc 驱动在 `SwapBuffers` 等 vsync 时自旋**（每帧约 16 ms CPU 时间）是已知行为吗？切到 eframe 的 wgpu 后端（DXGI flip model，present 阻塞而非自旋）能否规避？代价大概是二进制 +多少 MB、运行内存 +多少？
5. 如果目标是把"鼠标移动"的开销压到 5% 以内，是不是必须放弃"每次输入都整窗重绘"的架构（egui 不支持局部重绘）？有没有在 egui 生态内的推荐做法？

## 验收标准

- 鼠标在窗口内移动时：**帧率 ≤ 10 fps，CPU < 5% 单核**
- 鼠标静止：**1 fps，CPU < 1%**
- 保留悬停提示与十字线

# 解决方案（2026-11-19 已实现并验证）

## 根因：四条独立的「输入 → 整帧」链路 + 驱动的自旋等待

把 eframe 0.37.0 / egui-winit 0.37.0 / winit 0.30.13 的源码逐行查过之后，发现鼠标移动并不是
「触发一次重绘」，而是同时踩中**四条链路**；单独砍掉任何一条都修不好，这解释了此前所有
方案「结果不稳定」。

1. **egui-winit 无条件 `repaint: true`**
   `egui-winit/src/lib.rs` 里 `WindowEvent::CursorMoved` 固定返回
   `EventResponse { repaint: true, .. }`。eframe 的 Windows 后端（`glow_integration.rs`）
   把 `repaint` 变成 `EventResult::RepaintNow`，而 `run.rs` 在 Windows 上对 `RepaintNow`
   **同步执行一次完整 `run_ui_and_paint`**（egui#2280 防闪烁路径）。即：每个 `WM_MOUSEMOVE`
   = 一整帧。`raw_input_hook` 来不及救，因为重绘请求在事件到达 egui 之前就发出了。

2. **原始鼠标移动（DeviceEvent::MouseMotion）又请求一帧**
   winit 在 Windows 上默认 `DeviceEvents::WhenFocused`，前台窗口会收到原始鼠标移动；
   eframe 的 `device_event` 把它转发给 `on_mouse_motion`，只要指针在窗口内就返回
   `EventResult::RepaintNext` → `request_redraw` → 又一帧。这条与链路 1 完全独立，
   所以用 `SetCursorPos` 脚本测试时看不到（脚本不产生原始移动），真实鼠标则两条都踩。

3. **egui 自身的反馈环**
   egui 的 `InputState::wants_repaint_after()`：只要本帧有指针事件（`PointerMoved` 还在
   事件队列里），`Context::begin_pass` 就请求 `delay = 0` 的重绘 → 下一帧立即跑；
   下一帧又处理到新到的事件 → 再请求…… 只要鼠标还在动，这就是一个**自持的 60 fps 环**。
   这就是报告里「前台空闲也每帧一条 delay=0 请求」的来源。

4. **Intel Arc 的 GL 驱动在 vsync 交换里自旋**
   `SwapInterval::Wait(1)` 下 `SwapBuffers` 大约花 **16 ms CPU 时间/帧**（忙等下一个
   垂直同步而不是内核阻塞等）。所以即使把帧数压到 10 fps，纯交换也要 ~16% 单核；
   想达到「CPU < 5%」必须连这条一起解决。这是驱动行为，应用侧唯一的解法是**不走
   驱动的 vsync 等待**。

## 修复：四个部件，各砍一条链路

| # | 部件 | 砍掉哪条链路 |
| --- | --- | --- |
| 1 | `vendor/egui-winit`（`[patch.crates-io]` 本地补丁） | 链路 1/2：`CursorMoved`、`CursorLeft`、`CursorEntered` 都改为 `repaint: false` + `request_repaint_after(250ms)` 调度下一帧；`on_mouse_motion` 直接返回 `false`（不再逐条原始移动请求重绘） |
| 2 | `src/gui/throttle.rs` 的 `raw_input_hook` | 链路 3：丢弃队列里的 `PointerMoved`，每 250 ms 只放行**最新位置**一个事件（悬停位置仍然最新），`PointerGone` 同样限速（离开窗口是离散事件，也最多一个/时间片）；并把「待处理」状态提前调度到下一个时间片 |
| 3 | `GlowConfiguration { vsync: false }` + 每帧 `DwmFlush()` | 链路 4：交换不再进驱动忙等；`DwmFlush` 用内核阻塞重新对齐垂直同步，不撕裂、不耗 CPU |
| 4 | 图表悬停读数改为 `Painter` 直接绘制 | 附属：egui Tooltip 会「注册后下一帧渲染 + 动画期持续请求重绘」，多出 2~N 帧/次；内联绘制后悬停不再额外产生帧 |

关键常数：`vendor/egui-winit/src/lib.rs` 的 `MOVE_REPAINT_DELAY_MS = 250`（移动峰值 ~10 fps，
悬停 4 次/秒）。想要更跟手可改成 200（峰值 ~13 fps、CPU 约 +0.5%，悬停 5 Hz）。

改动文件：`vendor/egui-winit/`（含 `VENDORED.md` 说明补丁）、`src/gui/throttle.rs`（新增）、
`src/gui/app.rs`、`src/gui/chart.rs`、`src/gui/mod.rs`、`Cargo.toml`。

## 实测

测试方法同原报告：`Process.TotalProcessorTime` 增量/时间窗（占单核百分比），鼠标移动用
`PostMessageW(WM_MOUSEMOVE)` 以约 63 次/秒注入（沙箱内 `SetCursorPos` 被禁用，窗口消息不受限）。
帧率由应用内计数器逐秒记录；悬停读数用截图像素比对验证（悬停区 diffPixels=1822，
深色文本像素 124，即读数框与十字线已绘制）。

| 场景 | 修复前 | 修复后 | 目标 |
| --- | --- | --- | --- |
| 鼠标静止 / 在窗口外 | 1 fps · 0.5–0.9% | **1 fps · 0.3%**（干净测量；含启动尾迹/真实鼠标干扰时 ≤1.3%） | 1 fps · <1% |
| 鼠标在窗口内滑动 | 60 fps · 95–100% | **10.0 fps · 平均 2.8–3.0%**（逐秒样本多数 0–4.6%，真实鼠标叠加干扰时峰值 ~7.7%） | ≤10 fps · <5% |
| 滑动 + 窗口真实前台 | 60 fps · ~100% | **10.0 fps**（用户真实鼠标 177 事件/秒与合成移动叠加，帧率仍钉在 10） | ≤10 fps |

说明：移动中每帧结构是「1 个调度帧 + 1~2 个 egui 自身要求的立即帧」，所以 250 ms 时间片
对应 10 fps 峰值。帧率与 CPU 完全解耦了输入频率：63 次/秒与 177 次/秒的移动，帧率都是 10。

## 对原报告的五个问题的回答

1. **eframe 0.37 + glow 有没有公开 API 把输入驱动的重绘限到 10 fps？**
   没有。`Context::set_request_repaint_callback` 只能观察；`raw_input_hook` 在
   egui-winit 的 `repaint: true` 之后才执行；`NativeOptions::event_loop_builder` 拿不到
   窗口事件。唯一干净的做法就是上面这种本地补丁 + hook 组合。
2. **前台每帧 delay=0 的重绘请求来自哪里？**
   egui 自己：`begin_pass` 里 `InputState::wants_repaint_after()` 发现本帧有指针事件
   （`PointerMoved` 未消费或 `delta != 0`）就请求立即重绘，于是下一帧又处理到新事件……
   形成自持反馈环（链路 3）。
3. **有没有更早的钩子？** `raw_input_hook` 之前只有两处：eframe 的 winit 事件入口
   （无公开钩子）和 winit 的 Windows `msg_hook`（`EventLoopBuilderExtWindows`，只能整条
   吞消息，且会连位置一起丢）。本方案不吞消息：让事件继续入队，用 hook 限速放行 +
   携带最新位置。
4. **Intel Arc 在 `SwapBuffers` vsync 自旋是已知行为吗？切 wgpu 能否规避？**
   是，Windows 上 GL ICD 的 vsync 等待普遍是忙等，Intel 尤甚（前台 60 fps 时每帧
   ~16 ms CPU）。切 eframe 的 wgpu 后端（DXGI flip model）present 会正常阻塞，能规避，
   代价是二进制 +10~20 MB、运行内存明显上涨。本方案不换后端：vsync 关掉 +
   `DwmFlush()` 自配节奏，效果等价且零新增依赖。
5. **必须放弃「每次输入都整窗重绘」吗？** egui 确实不支持局部重绘。但只要把
   「输入→帧」的转化率从 1:1 降到 1/200ms，整窗重绘的成本就无所谓了（本帧内容
   212 µs + 渲染 ~1.2 ms）。不需要换架构。
