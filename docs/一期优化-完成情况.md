## 逐项说明

### 一.1 内存：字体改为内存映射（收益最大）

原建议用 `fonttools subset` 把雅黑裁成子集再打包进二进制。没有照做，有两个原因：

1. **微软雅黑是商业字体，不允许随程序分发**——即使裁成子集，把字形数据提交进公开仓库仍有授权风险。
2. 子集化需要引入构建期工具链（fonttools）或第三方 Rust 子集库，与"零依赖"的取舍相反。

实际做法是让字体**不进入私有提交**：用 `CreateFileW` + `CreateFileMappingW` + `MapViewOfFile` 把系统字体映射进地址空间，再通过 `FontData::from_blob` 直接吃这块内存（epaint 原生支持共享字节，零拷贝）。映射页是文件页，可被系统回收，不计入 `PrivateUsage`；字体依旧来自系统，没有分发问题，也没有新增依赖。

结果：私有内存 **84.9 → 65.4 MB**，工作集 **116 → 97 MB**，启动时也不再往堆里读 19 MB。映射失败时自动退回 `std::fs::read`。

### 一.2 历史数据：核实后不改

`Ring` 当前是 `Vec<f32>` + 固定容量（`with_capacity`），push 复用同一块内存，不存在"每帧新 Vec"的情况。9 条曲线 × 900 点 × 4 字节 ≈ **32 KB**，即使全部换成 `MaybeUninit` 定长环，节省也在 0.1 MB 以内，却要引入 unsafe 代码。保留现状，并在测试里锁定了容量行为。

### 一.3 / 一.4 / 一.5：不适用或收益为负

- 没有进程列表，所以没有"463 个进程每帧重新收集"。
- egui 0.37 没有 `purge_cache`；图表全部是即时绘制的图元，不产生滞留纹理。
- `opt-level="z"` 目标是代码体积，对内存无帮助，还会牺牲采样与渲染速度。已启用 `lto=fat`、`codegen-units=1`、`strip`、`panic=abort`。

### 二 系统主题（已完成）

`RegGetValueW` 读 `HKCU\...\Themes\Personalize\AppsUseLightTheme`，`0` 为暗色、`1` 为浅色，不需要 `windows-registry` crate。默认跟随系统，`--light` / `--dark` 可强制覆盖。本机当前是浅色，所以默认启动即浅色。

### 四 温度 Y 轴（已完成）

不再固定 30–100 °C，而是取**可视窗口**的温度 min/max，生成 40–70 °C 的跨度，围绕中心对齐到 5 °C，再夹在 20–105 °C 之间。86 °C 时轴为 65–105，曲线占满卡片而不是压在上沿；温度升高时窗口自动下移。

### 五 每核悬浮提示（已完成）

采集侧新增 `sys::cpu::frequencies()`：`CallNtPowerInformation(ProcessorInformation)` 返回的数组按逻辑处理器解析，拿到**每核当前 MHz**（此前只取平均值）。悬浮提示从"核心 N / 23%"升级为"核心 N / 使用率 / 当前频率"。

### 六 颜色与峰值（已完成）

- 颜色按建议换成分明的一对：网络下行 `#4FC3F7` / 上行 `#FF7043`；磁盘读 `#66BB6A` / 写 `#FFA726`（浅色主题用对应的深色变体）。原先上行复用内存色、写入复用温度色，确实容易混。
- Y 轴改为"可视窗口 P90 × 1.15 后取整，再按 0.3 的系数平滑"：空闲时轴会收缩，不会一直贴着历史峰值；负载变化时轴平滑过渡而不是跳变。

### 七 开机时间（已完成）

GUI 头部显示"运行 1天23时45分"，复用现有的 `GetTickCount64` 实现，与 TUI 一致。

### 三 / 八 / 九：二期

- **进程管理**：`NtQuerySystemInformation(SystemProcessInformation)` + 每进程 CPU 增量 + 排序表 + 结束进程（提权失败提示）。是一整块独立功能。
- **硬件信息**：主板/BIOS/内存条需要 WMI，显存需要 DXGI；CPU 型号与核数已有。
- **GPU**：PDH `\GPU Engine(*)\Utilization Percentage` 可行，但要按适配器聚合大量实例，独立成一章更清楚。

### 十一 架构拆分（不做）

建议里的 `gui/cards/*`、`gui/charts/*`、`gui/widgets/*` 目录，对当前 ~1200 行的 GUI 属于过度设计。现在的 `gui/{app,chart,theme,font}.rs` 已经按"状态 / 绘制 / 配色 / 字体"分开，再加一层目录只会让跳转变多。

## 为什么没做到 40 MB

65 MB 的构成里，字体已经不在私有提交中，剩下的主要是 egui/glow 的渲染资源、窗口表面与显卡驱动分配。对照实验：一个只有几个控件、同样加载中文字体的**最小 egui 窗口**，`from_owned` 时也要约 79 MB——说明大头不是我们的界面代码。

要继续压只有两条路：换渲染栈（自绘 GDI 能到 10 MB 级，等于重写界面），或退回 TUI（6.8 MB）。这是选型时的既有结论，不是本期没做够。
